# VOICEVOX Leaderboard

VOICEVOX Organization の GitHub 貢献を実データから試算する静的リーダーボードです。
関連 Issue が同じマージ済み PR を一つのワークストリームへまとめ、未マージ PR は一件ずつ扱います。
実装、レビュー、Issue と調査を一つの点数へ変換します。

この実装は指標を検証するためのプロトタイプです。
サーバーサイド処理はありません。

## 構成

GitHub API の取得、本文解析、変更ファイルの重み付けはデプロイ前に Node.js で実行します。
取得結果は `public/data/leaderboard-data.json` へ保存します。

ブラウザは事前処理済みデータだけを読み込みます。
選択期間の PR と Issue 活動を絞り込み、ワークストリームの配点を再計算します。
GitHub token はブラウザへ渡しません。

対象は VOICEVOX Organization の公開かつ非アーカイブな全リポジトリです。
fork と mirror も対象に含みます。
対象を画面や設定で変更する機能はありません。

AI へ実装させる前提で運用しているリポジトリは `config/fullAiRepositories.json` へ owner/name 形式で書きます。
設定は取得時に読み込み、対象リポジトリにない指定は警告を出します。

## データ取得

Node.js 24 と pnpm 10 を使用します。

    pnpm install --frozen-lockfile
    GH_TOKEN="$(gh auth token)" pnpm fetch-data -- --months 3

`GH_TOKEN` または `GITHUB_TOKEN` が必要です。
トークン値は成果物へ保存しません。

日付を直接指定する場合は次のように実行します。

    GITHUB_TOKEN=github_pat_xxx pnpm fetch-data -- --start 2026-05-02 --end 2026-08-02

取得キャッシュは `.cache/github` に保存します。
各 API 応答は ETag または Last-Modified で再検証するため、キャッシュの有無によって採点対象データは変わりません。

Organization 全体を検索して候補を集め、リポジトリごとの検索を行わないことで Search API の消費を抑えます。
Core API は最大 8 並列で取得し、残量が 50 以下になるとリセットまで待機します。
Search API は直列化し、呼び出し間隔を 2.1 秒以上空けます。
巨大な差分を REST API が生成できない PR は、GraphQL API から変更ファイルを取得します。
PR 詳細の変更ファイル数とファイル一覧の件数が食い違う場合は、条件付きリクエストを使わずに両方を取り直します。
GitHub API が一時的に誤った変更ファイル数を返すことがあり、その応答がキャッシュへ固定されるためです。

## 起動

事前取得データを生成してから開発サーバーを起動します。

    pnpm dev

ヘッダーの期間ボタンから、取得済み期間内の開始日と終了日を指定できます。
期間ボタンのダイアログには、表示しているデータの生成日時も表示します。
URL に期間指定がない場合は直近 7 日を表示し、URL を `?period=7d` へ置き換えます。
直近期間を選ぶと、`period` クエリパラメータを持つ URL になります。
`?period=7d` は直近 7 日、`?period=2w` は直近 2 週間、`?period=1m` は直近 1 か月を表します。
直近期間は取得済みデータの終了日を基準に計算するため、データ更新後も同じ URL で最新期間を表示します。
日付を直接指定した場合は `start` と `end` を URL に保持します。
トップページにはリーダーボードだけを表示します。
ヘッダーから全 PR、全 Issue、計算式のページへ移動できます。
リーダーボードと各一覧から人物、PR、Issue の詳細ページへ移動できます。
GitHub の各ページへの外部リンクは対応する詳細ページにだけ表示します。

人物、PR、Issue の詳細ページでは、PR、Issue、人物をたどって配点元を確認できるサンキーダイアグラムを表示します。
実装とレビューは PR から人物へ直接つなぎ、Issue と調査は PR から関連 Issue を経て人物へつなぎます。
独立 Issue の経路は Issue から始まります。
同じ PR、Issue、人物は一つのノードにまとめ、同じ始点・終点・配点種別の経路は点数を合計して一つの帯にまとめます。
実装、レビュー、Issue と調査はノードにせず、帯の色で区別します。
配点対象外の点はサンキーダイアグラムに表示しません。
サンキーダイアグラムは内容に必要な高さをすべて表示し、図内に縦スクロールを作りません。

サンキーダイアグラム以外の点数内訳は積み上げ棒グラフで表示します。
種類順は実装、レビュー、Issue と調査、配点対象外で統一しています。
配点対象外の点がないグラフでは先頭の 3 種類だけを表示します。
リーダーボードでは最高得点者の合計をバーの最大値とし、各人の点数を相対的な長さで表示します。
人物詳細では表示中の人物の合計をバーの最大値とします。

画面内リンクはハッシュを使わない URL です。
GitHub Pages で個別ページを直接開けるように、ビルド時に同じ起動ページを `404.html` にも配置します。
全ページに検索エンジン向けの noindex を設定しています。

## デプロイ

`.github/workflows/deploy.yml` は 6 時間ごとに開始し、過去 3 か月のデータを取得して GitHub Pages へデプロイします。
開始時刻は日本時間の 0 時、6 時、12 時、18 時です。
`workflow_dispatch` から手動でも実行できます。

データ取得のあとに lint、型検査、テスト、ビルドを実行し、すべて成功した場合だけデプロイします。
Workflow は `.cache/github` を Actions cache へ保存し、次回のデプロイで再利用します。
実行が重なった場合は直列化し、実行中のデプロイを中断しません。

ブラウザは起動時にデータを一度だけ読み込みます。
開いたままの画面に新しいデータは反映されないため、更新の反映には再読み込みが必要です。

GitHub リポジトリの Pages 設定では Source に GitHub Actions を指定してください。

## 検証

    pnpm lint
    pnpm typecheck
    pnpm test
    pnpm build

`.github/workflows/ci.yml` はプルリクエストと `main` ブランチへの push で開始し、上記をすべて実行します。
実行が重なった場合は、同じ ref の実行中の CI を中断して新しい実行を開始します。

## 計算内容

- 同じ主 Issue を参照するマージ済み PR を一つにまとめる
- 未マージ PR は一件ごとに扱い、関連 Issue 枠を配分しない
- 変更行、非生成ファイル数、リポジトリ数、Conventional Commits 補正から重要度を求める
- 重要度を実装最大 65%、レビュー 20%、Issue と調査 15%へ配分する
- PR の状態を選択期間の末日時点で判定し、実装枠をマージ済みは 1 倍、オープンは 0.5 倍、クローズ済みは 0.25 倍にする
- 独立した品質確認がない場合、マージ済み PR では実装枠の半分、未マージ PR では実装枠の全部を配点対象外とする
- レビュー枠には状態係数を掛けない
- フルAI実装リポジトリでは変更ファイルをすべて生成物として数え、実装枠の 30%だけを配分する
- 関連するマージ済み PR がない Issue に独立 Issue スコアを与える
- Bot の活動を除外する
- 各人、PR、Issue から算出根拠を確認できるようにする
- PR 作者、共同作者、レビュー総評、レビュースレッド、Issue 作成、本文の証拠要素、Issue コメントを個別の配点明細として保持し、サンキーダイアグラムでは同じ属性の経路を集約する
- 人物へ配点された点と配点対象外の点の合計をワークストリーム重要度と一致させる

Issue とレビューの実質判定には、本文量に加えてコマンド、ログ、添付、参照、環境、測定値を使います。
PR ごとの AI 利用の記載自体は採点条件にせず、独立した人間の品質確認をすべての実装へ同じ条件で適用します。
判断根拠と VOICEVOX での実例は [レビュー保証調査](docs/レビュー保証調査.md)、[フルAI実装調査](docs/フルAI実装調査.md)、[未マージPR調査](docs/未マージPR調査.md) にまとめています。
