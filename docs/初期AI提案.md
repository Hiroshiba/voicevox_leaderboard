# 結論

VOICEVOXでは、**月間の「成果連結型貢献スコア」**を1つだけ出すのが妥当です。

単純な「PR数 × 点数」「コメント数 × 点数」ではなく、次の構造にします。

> **関連Issueが同じPR群を1つのワークストリームとしてまとめ、その月に受け入れられた成果の規模・範囲を対数評価し、実装者・人間レビュアー・Issue上の調査／設計参加者へ配分する。**

最終的なランキングには、各人の合計値だけを表示します。内部的には複数種類の活動を扱いますが、部門別ランキングには分けません。

また、このスコアが測るのは**人間が費やした時間や苦労ではなく、VOICEVOXに受け入れられた成果と、そこへ至る検証・レビュー・設計への貢献**です。AIを使ったかどうかで補正せず、Bot自身の活動だけを除外します。

# 1. VOICEVOXの実態調査

## 直近PRの構成

GitHub検索で取得した、2026年5月9日から7月27日までの直近100件のPR標本を、タイトルの接頭辞で機械的に分類しました。標本の始点はEngine #1860、終点はEditor #3077です。

| タイトル種別                       | 件数 |
| ---------------------------- | -: |
| `feat`                       | 28 |
| `chore`                      | 19 |
| `fix`                        | 14 |
| `refactor`                   |  9 |
| `test`                       |  8 |
| `docs`                       |  6 |
| `ci`                         |  4 |
| `build` / `build!`           |  2 |
| `style`                      |  1 |
| Conventional Commits形式ではないもの |  9 |

したがって、**約91%はConventional Commits風の分類が可能**です。これは自動分類の入力としては十分使えます。

ただし、重要度判定には使えません。

たとえば、次の二つはどちらも通常の1PRですが、性質が大きく異なります。

* Editor #3077は、1ファイル・23行追加のE2Eテストです。
* Editor #3074は、22ファイル・345行追加・571行削除で、保存形式、合成処理、バリデーション、UIを横断します。

逆に、`chore`でも重要なものがあります。

* `onnxruntime-builder` #112は、1ファイル・5行追加・6行削除ですが、CUDA・cuDNNのビルド構成を更新する変更です。
* `voicevox_additional_libraries` #22は、2ファイル・9行追加・12行削除ですが、Windows配布物が813 MiBから961 MiB、Linux配布物が803 MiBから999 MiBになるライブラリ構成変更です。

したがって、**Conventional Commitsのtypeは小さな補助係数としてのみ使用**し、主成分にはできません。

---

## PR数をそのまま数えると、適切なPR分割が点数水増しになる

ソングのボリューム編集Issue #2733には、調査時点で26件のコメントがあります。さらに、このIssueを参照するPRが少なくとも10件あります。

* 型・スキーマ
* ドメインロジック
* Store・ステートマシン
* UI
* パン・ズーム
* 編集可能領域
* グリッド・ツールチップ
* 相対値化
* 相対dB保存

といった形で、意図的かつ妥当に分割されています。

音素タイミング編集Issue #2261でも、波形表示、ノート表示、音素表示、Store、推論への適用、最終的な編集機能などが別PRになっています。

この実態では、次の方式はいずれも不適切です。

* マージPRを1件10点
* `feat` PRを1件20点
* 変更行数に比例して加点
* PRのコミット数やレビュー往復数に比例して加点

VOICEVOXでは、**PRではなく関連Issueを単位とする必要があります**。

---

## 複数リポジトリにまたがる一つの作業がある

`voicevox_project` #99は、ONNX Runtime 1.23.2への更新をリポジトリ横断プロジェクトとして管理しています。Issue本文でも、横断するため`voicevox_project`にIssueを作ったと明記されています。

関係する作業には、少なくとも次があります。

* `onnxruntime-builder`のCUDA・cuDNN更新
* `voicevox_additional_libraries`の配布ライブラリ更新
* Coreの対応
* Engineの更新
* 最終的なEditor追従

個々の差分は小さくても、整合するバージョンの選定、実機検証、配布物構成、互換性確認が必要です。Core側PRは複数の関連Issue・PRを参照し、Engine側は依存作業待ちのDraftになっています。

したがって、リポジトリごとの固定係数ではなく、**同じ関連Issueを参照して複数リポジトリを変更した場合の横断範囲**を評価する必要があります。

---

## PRにならないIssue貢献が実際に重い

Editor #2790は、Linuxビルド時にPlaywrightやElectronのキャッシュが大きくなるという具体的な報告です。コマンド、容量、環境、再現状況を含み、21件のコメントで挙動確認や代替案の検証が行われ、翌日に`completed`で閉じられています。番号参照でPRを検索した範囲では、対応PRは見つかりませんでした。

Engine #1795は、既存PRの品質検証だけを目的としたIssueです。16種類の入力音声を4話者で生成する試験、ノイズ耐性、音量耐性などを実施し、結果ファイルをIssueへ添付するよう求めています。コードを書かなくても、相当に重い貢献になり得ます。

したがって、Issueでは少なくとも以下を評価対象にする必要があります。

* 再現可能な不具合報告
* 測定や比較結果
* 設計案・代替案
* 実機検証
* 音声・画像・ログ等の添付
* 既存仕様や過去経緯の調査
* PRにならず、Issue上の結論だけで完了した調査

ただし、コメント件数をそのまま点数にすると、長文や往復を増やす誘因になるため、件数は対数化・上限制にすべきです。

---

## AI利用者と非利用者を自動判別するのは不可能に近い

Editor #3075は、Claude Opus 5で作成したことを明示したうえでマージされています。別のPRでも同様の開示があり、UIモック調査ではAIプロトタイピング目的が明記されています。

一方、すべてのAI利用が開示される保証はありません。これは公開情報からの推論ですが、開示文があるPRだけをAI利用扱いすると、開示した人だけが不利または有利になります。

したがって、

* **人間アカウントが責任を持って提出した成果は、AI利用の有無に関係なく同じ式で評価**
* **GitHub上でBotと判定できるアカウントは0点**
* Copilot等のレビューBotも0点
* AI利用開示文はスコア計算に使わない

とするのが妥当です。

# 2. 推奨する単一指標

名称は仮に、**VOICEVOX Contribution Score**とします。

公式ランキングは週次ではなく、**月間ランキング**を推奨します。VOICEVOXでは、一つの変更が設計・実装・レビューを含めて複数週にまたがることが多く、週間ランキングでは小さく早いPRが過度に有利になるためです。

最終的な個人スコアは次です。

[
\text{Score}_{u}
================

\text{実装ポイント}*{u}
+
\text{レビューポイント}*{u}
+
\text{Issue・調査ポイント}_{u}
]

これはあくまで内部計算です。公開ランキングでは合計値だけを使用します。

# 3. PRを「ワークストリーム」にまとめる

## ワークストリームキーの決定

各PRについて、次の順で主たる関連Issueを自動決定します。

1. `close`、`closes`、`fix`、`fixes`、`resolve`、`resolves`で指定されたIssue
2. PR本文の`関連 Issue`セクションに最初に書かれたVOICEVOX Organization内のIssue
3. 関連PRを参照している場合、そのPRの主たる関連Issueを1段だけたどる
4. どれもない場合は、そのPR自体を独立ワークストリームとする

同じ月にマージされ、同じ主Issueを持つPRは、リポジトリをまたいで1ワークストリームにまとめます。

これにより、

* #2733を参照する複数のボリューム編集PR
* #2261を参照する複数の音素タイミング編集PR
* `voicevox_project` #99を参照するONNX Runtime更新群

が、それぞれ一つの成果単位になります。

**PR件数そのものは式に入れません。**

# 4. ワークストリームの重要度計算

推奨する初期式は次です。

[
I(W)=\min\left(
15,;
1
+1.5\log_2(1+E/20)
+0.5\log_2(1+F)
+\log_2(R)
+C
\right)
]

| 変数   | 意味                             |
| ---- | ------------------------------ |
| (E)  | 有効変更行数                         |
| (F)  | 非生成ファイルの変更ファイル数                |
| (R)  | 変更がマージされたVOICEVOX内リポジトリ数       |
| (C)  | Conventional Commits等から得る小さな補正 |
| 上限15 | 一つの巨大作業だけで月間ランキングが決まるのを防ぐ      |

## 有効変更行数 (E)

各ファイルについて、追加行数と削除行数を合計します。ただし、1ファイル当たり200行を上限にします。

| ファイル種類                           |   係数 |
| -------------------------------- | ---: |
| 通常のソース、テスト、ビルド、CI、設定             |  1.0 |
| Markdown等の文章中心ファイル               |  0.5 |
| 自動生成コード、lockfile、snapshot、vendor | 0.05 |

テストコードは通常コードと同じ1.0です。VOICEVOXでは、Editor #3049のようなflakyテスト修正が実際の開発効率へ直接影響するためです。#3049は1ファイルのみですが、実時間依存を決定論的な検証へ置き換え、高負荷時の反復確認まで行っています。

文章を0.5にするのは、価値が低いからではなく、文章の改行数とコード行数をそのまま比較できないためです。

## Conventional Commits補正 (C)

| 最終的なマージコミットの種別                                            |  (C) |
| --------------------------------------------------------- | ---: |
| `!`、`BREAKING CHANGE`、明示的なセキュリティ修正                        |  1.5 |
| `feat`、`fix`、`perf`                                       |  1.0 |
| `test`、`build`、`ci`、`refactor`、`docs`、`chore`、`revert`、不明 |  0.5 |
| `style`のみ                                                 | 0.25 |

使用するのは、変更可能な途中時点のPRタイトルではなく、**マージ時点の最終タイトルまたはsquash commitのsubject**です。

`feat`を`fix`より高くしていないのは、バグ修正と機能追加のどちらが重要かを自動判定できないためです。

# 5. 実装・レビュー・Issueへのポイント配分

ワークストリームの重要度 (I(W)) を、そのままPR作者だけに渡しません。

| 貢献              |  最大配分 |
| --------------- | ----: |
| 実装・PR作成         | (65%) |
| 人間によるレビュー       | (20%) |
| Issue作成・調査・設計議論 | (15%) |

未使用のレビュー枠やIssue枠を実装者へ戻さないことを推奨します。そうしないと、「レビューを受けない方が作者の点が高い」という誘因が発生するためです。

## 実装ポイント

[
\text{実装枠}=0.65I(W)
]

同じワークストリームに複数PR・複数作者がいる場合は、各PRについて次の質量を求めます。

[
M(p)=
1+\log_2(1+E_p/20)+0.5\log_2(1+F_p)
]

この比率で実装枠を分配します。

PR内に人間のcommit authorや`Co-authored-by`が複数いる場合は、

* PR作者に70%
* その他の人間の共同作者へ30%

を配分します。共同作者がいなければPR作者が100%を受け取ります。

これにより、PRを細かく分割してもワークストリーム全体の点数は増えず、複数人で分担した場合だけ各人へ適切に分かれます。

## レビューポイント

レビューBot、PR作者自身の返信、単なる「修正しました」「ありがとうございます」は除外します。

レビュー者ごとの重みは次です。

[
V(r)=
1
+\min(3,\text{開始した実質的レビューthread数})
+\text{実質的な総評があれば1}
]

レビュー枠の実際の使用量は、

[
0.20I(W)\times
\min\left(1,\frac{\sum V(r)}{5}\right)
]

です。

つまり、

* コメントなしのApproveだけなら少量
* 具体的な指摘を複数行ったレビューなら大きく加点
* 5以上の重みになっても上限は20%

となります。

Editor #3074には、Copilotによるレビューと、人間によるデータ型・命名・バリデーション等のレビューが混在しています。単純なコメント数ではBotコメント、作者の返信、人間の設計指摘が同じ1件になりますが、この方式では人間が開始したレビューthreadだけが対象です。

# 6. Issue・調査貢献の自動判定

## 「実質的なIssue／コメント」の条件

文字数だけではなく、以下の証拠要素を検出します。

* コードブロック、ログ、スタックトレース
* 再現コマンド
* 音声、画像、ファイル等の添付
* commit、PR、Actions run、upstream Issue等への参照
* OS、バージョン、実行環境の具体的記載
* 表、容量、処理時間、ベンチマーク等の測定値

コメントは、引用と定型文を除いた本文が一定量以上あるか、上記の証拠要素を一つ以上持つ場合に「実質的」とします。

本文の長さ自体は点数にしません。

## PRにつながったIssue

ワークストリームのIssue枠は最大で、

[
0.15I(W)
]

です。

Issue上の参加者へ次の重みを与え、その比率で配分します。

| 活動                |          重み |
| ----------------- | ----------: |
| Issue作成           |           2 |
| Issue本文内の証拠要素     | 1要素につき1、最大4 |
| 実質的コメント           |         基本1 |
| 添付・ログ・測定結果を伴うコメント |         追加1 |

同じ人が同じIssueへ大量に投稿しても、月内で評価するコメントは最大3件とし、重みを

[
1,;0.5,;0.25
]

と逓減させます。

したがって、29コメントあるIssueでも29倍にはなりません。

## PRにならなかったIssue

関連するマージ済みPRがないIssueには、独立したIssueスコアを与えます。

[
J(I)=\min\left(
8,;
B
+0.5\min(Q,4)
+\min(3,\log_2(1+S))
+\min(1.5,0.75\log_2(1+H))
\right)
]

| 変数  | 意味               |
| --- | ---------------- |
| (B) | 状態ボーナス           |
| (Q) | 証拠要素数            |
| (S) | 実質的コメント数         |
| (H) | Issue作者以外の人間参加者数 |

状態ボーナスは次です。

| 状態                             | (B) |
| ------------------------------ | --: |
| `completed`でClose              |   2 |
| Openだが検証条件を満たす                 |   1 |
| Duplicate／Not plannedだが有用な証拠あり | 0.5 |
| Invalid／Spam相当                 |   0 |

Open Issueを有効とする条件は、次のいずれかです。

* 作者以外の人間が2人以上、実質的に参加
* 作者以外の人間が1人以上参加し、証拠要素が2種類以上
* 明示的な検証タスクとして、添付物や測定結果が投稿されている

Editor #2790のような再現・検証型Issueは上限に近い点になります。Engine #1795のような音声品質検証も、添付された実験結果を含めてIssue貢献として評価できます。

Issueイベントには一意なIDを持たせ、一度加点したIssue作成・コメントを、後でPRがマージされたときに再加点しないようにします。

# 7. 実際のVOICEVOX PRへ式を当てた場合

以下は、ファイルごとの生成物判定を行わず、すべて通常ファイルとして計算した**ワークストリーム総点の上限寄り概算**です。作者個人が受け取るのは、このうち実装枠の最大65%です。

| 対象                                    |                  変更量 | 概算 (I(W)) | 扱い                     |
| ------------------------------------- | -------------------: | --------: | ---------------------- |
| Editor #3077 E2E追加                    |            1ファイル、+23 |      約3.7 | 小規模だが受け入れ済みのテスト貢献      |
| Editor #3049 flakyテスト修正               |        1ファイル、+49/-48 |      約5.8 | 1ファイルでも調査・検証量を反映       |
| Editor #3067 エンジン分離ビルド                |      10ファイル、+157/-31 |      約8.8 | 配布経路変更として中～大規模         |
| Blog #380 フォントサブセット                   |       47ファイル、+251/-1 |     約10.4 | 生成物を除外すると少し下がる可能性あり    |
| Core #1362 `build!`                   |       8ファイル、+207/-12 |      約9.5 | Breaking補正を含む          |
| Editor #3074 ボリューム相対編集                |     22ファイル、+345/-571 |     約12.6 | 現在Openなので公式点は0。マージ後に加点 |

一方、ONNX Runtime更新は複数リポジトリへ進展するたび、(R)、(E)、(F)が増えます。小さなバージョン変更PRだけを個別評価するより、実態に近い値になります。

# 8. 使用しない方がよい指標

| 候補             | 採用しない理由                            |
| -------------- | ---------------------------------- |
| PR件数           | VOICEVOXでは適切な分割PRが多く、容易に水増しされる     |
| コミット数          | fixupやAIの作業方法、squash前の履歴に依存する      |
| 変更行数への線形比例     | 生成コード、lockfile、大規模移動で壊れる           |
| コメント件数への線形比例   | 長いやり取りや細切れ返信を増やす誘因になる              |
| レビュー往復回数       | 初期品質が低いPRほど点が増える可能性がある             |
| Issueの経過日数     | 放置期間やレビュー待ちを貢献者の功績・責任として扱ってしまう     |
| PR作成からマージまでの時間 | メンテナー側のレビュー速度に強く依存する               |
| 初動の速さ          | タイムゾーン、生活時間、常時監視可能性を評価してしまう        |
| リアクション数        | 技術的価値より知名度・人気を反映しやすい               |
| 優先度・重要度ラベル     | リポジトリ間で運用が統一されておらず、人手判定になる         |
| AI利用の有無        | 確実に観測できず、開示した人だけが影響を受ける            |
| LLMによる重要度採点    | 再現性が低く、PR本文を長くする・プロンプトを埋め込む等の攻略が可能 |

「素早い対応」は価値がありますが、今回の単一スコアには入れない方がよいです。古いIssueを不利にする年齢減衰も入れません。

古いIssueであっても、対象月に実質的な調査コメント、検証結果、Close、マージ済みPRが発生すれば、その活動は通常どおり計上されます。

# 9. リポジトリ間の固定ウェイトは設けない

Coreを2倍、Blogを0.5倍、という設定は行わない方がよいです。

* Blog #380のように、サイト性能や配布量へ影響する大きな変更がある
* 小規模リポジトリへ小さな変更を出す方が有利になる
* リポジトリの重要度をメンテナーが継続的に決める必要が生じる
* リポジトリ横断変更を評価しにくくなる

すべて同じ式で計算し、複数リポジトリへまたがった場合だけ(\log_2(R))を加える方が安定します。

対象リポジトリは、Organization内の全リポジトリを自動包含するのではなく、**アクティブな一次管理リポジトリのallowlist**にします。fork、mirror、アーカイブ、外部ソースの同期用リポジトリを除外するためです。これは初期設定であり、PRごとの人手判定ではありません。

# 10. AI利用者への扱い

AI利用者を減点しないことを推奨します。

VOICEVOXでAI利用が多い場合、ランキングが測るべきものを明確に分ける必要があります。

| 測定対象              | 自動ランキング可能性 |
| ----------------- | ---------- |
| 受け入れられた成果         | 可能         |
| レビュー・調査・Issue貢献   | ある程度可能     |
| 人間が費やした時間         | 不可能        |
| AIがなければ必要だった労力    | 不可能        |
| 本人がどの程度AI出力を理解したか | 自動判定困難     |

したがって、このランキングは**努力ランキングではなく成果貢献ランキング**です。

AIを使って多くの変更を出しても、

* マージされなければ実装点は0
* 同じIssueでPRを分割しても総点は増えない
* 生成コードは大幅に割り引かれる
* Botレビューは0
* 大量コメントは逓減する
* 人間レビューとIssue調査にもポイントが配分される

ため、単純なAI大量生成だけでは上位へ行きにくい構造になります。

# 11. 運用方法

最初から公開ランキングにせず、**過去6か月分をシャドー計算**するのが妥当です。

検証すべき基準は次の5点です。

| ケース              | 期待結果                          |
| ---------------- | ----------------------------- |
| #2733の10件の分割PR   | PR数10倍にはならず、一つの大きなワークストリームになる |
| #2790のIssue調査    | PRなしでも意味のある点になる               |
| #1795の音声検証       | 添付・測定を行った参加者へ点が入る             |
| #3074のレビュー       | Copilotは0、人間の具体的レビューに点が入る     |
| ONNX Runtime #99 | 小差分でも複数リポジトリ横断により中程度以上になる     |

調整するときは、特定の人やPRに合わせて例外を追加せず、

* 上限15
* 65%／20%／15%
* 行数の基準20
* Issue上限8
* 証拠要素の閾値

といった**全体定数だけを変更**します。

ランキング公開時には、合計スコアだけでなく、各人について「どのワークストリームから何点入ったか」を展開可能にしておくべきです。部門別ランキングを作る必要はありませんが、計算根拠が見えない単一スコアは不信感を生みやすいためです。

VOICEVOXの`CONTRIBUTING.md`では、コードやドキュメント以外に、利用、記事、動画等も貢献として扱っています。ただし、完全自動かつGitHub内だけで判定する今回のランキングでは、GitHub上で観測可能な活動に対象を限定する必要があります。

**最終的な推奨仕様は、「月間・関連Issue単位・マージ成果中心・Issue単独貢献あり・人間レビューあり・AI補正なし・Bot除外」の一つのスコアです。**
