# 編集量スコアの検証

GitHub API から代表的な 8 PR の変更ファイルと差分を取得し、字句差分から編集量を計算しました。
通常コードの重みは 1、文書は 0.5 とし、生成物を持つワークストリームには補助量 1 を加えています。
計算式と制約は [コード差分の算定](コード差分の算定.md) を参照してください。

比較基準はコミット `b561450` の実装です。
どちらもリポジトリ数 1、タイトル補正 0、フルAI実装指定なしで計算しました。
レビュー、PR の状態、人物への配分は含まない、コード由来重要度の単独換算です。
新旧の尺度は校正していないため、数値の比率を貢献度の比率とは解釈しません。

この 8 PR に未測定のファイルはありません。
生成物は通常の編集量とは別に分類しています。
Blog #330 の 162 ファイルはすべて生成物であり、編集量 U は 0、補助量 G は 1 です。
Core #69 は 8 回の置換を、文書とコードで重みの異なる 2 グループにまとめました。
README 内の 6 回と requirements.txt 内の 1 回は同じ編集として圧縮しています。

Blog #250 と Engine #1817、Core #69 と Builder #114、Editor #2871 と Engine #1817 の順序が行数方式から逆転しました。
これらは反復や再インデントへの感度を確認する実例であり、変更の機能上の価値を証明するものではありません。
YAML の空白や JavaScript の改行、コメントも保守的に数えるため、別の字句解析器で計算した試作値とは一致しません。

## 保存済みデータ

保存済み 188 PR のファイル差分を再取得し、編集量方式のスキーマへ更新しました。
PR、Issue、期間、生成日時には保存済みの情報を使い、差分の再解析日と未測定件数はデータ内の notices に記録します。
ファイル一覧や変更行数が保存済みの統計と一致しない 8 PR と、REST API が 422 を返した 1 PR では、過去の差分を復元できない部分を未測定として残しています。
元のファイル統計を保持し、現在の差分から過去の変更量を推測していません。

これは保存済みデータの再解析と代表例の検証です。
100 PR を新たに抽出して貢献の価値を人手で評価した調査ではありません。
